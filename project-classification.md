# Класифікація проєкту та аналіз проєктного оточення

**Проєкт:** EduTrack - персональний кабінет студента з оцінками, дедлайнами, статистикою відвідуваності та прогнозом підсумкової оцінки

---

## 5.1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
|---|---|---|
| Розмір проєкту | Малий | Проєкт розробляється невеликою студентською командою в межах навчального курсу з обмеженим часовим бюджетом і без залучення зовнішнього фінансування чи великої кількості учасників. |
| Тип продукту | Веб-застосунок | EduTrack реалізується як веб-платформа з фронтендом і бекендом, доступ до якої здійснюється через браузер, без потреби у встановленні окремого клієнта. |
| Галузь застосування | Освіта | Продукт вирішує задачі студента у навчальному процесі: відстеження оцінок, дедлайнів, відвідуваності та прогнозування підсумкового результату. |
| Рівень невизначеності вимог | Середній | Базовий функціонал (оцінки, дедлайни, відвідуваність) чітко визначений, проте деталі реалізації прогнозної моделі оцінки та можливі додаткові інтеграції можуть уточнюватися в процесі розробки. |
| Модель співпраці | Внутрішній продукт (навчальний проєкт) | Проєкт виконується командою в межах курсу без зовнішнього замовника; рішення щодо функціоналу приймає сама команда за погодженням з викладачем. |
| Тип життєвого циклу | Ітеративний / Agile | Розробка ведеться поетапно через послідовні лабораторні роботи, кожна з яких додає новий шар функціоналу та документації, що відповідає ітеративному підходу. |

---

## 5.2. Аналіз внутрішнього оточення

- **Склад і компетенції команди.** Команда складається з учасників з різним рівнем підготовки у фронтенд- та бекенд-розробці; частина учасників має базові навички роботи з React/Node.js та системами контролю версій (Git/GitHub).
- **Наявні технічні ресурси.** Команда використовує безкоштовні інструменти: GitHub для контролю версій, безкоштовні хостинги для розгортання, відкриті бібліотеки та фреймворки без ліцензійних обмежень.
- **Часовий бюджет команди.** Обмежена кількість годин на тиждень.
- **Досвід учасників з обраною тематикою.** Частина команди раніше працювала з подібними CRUD-застосунками, проте досвіду розробки прогнозних алгоритмів (для передбачення підсумкової оцінки) в команди немає, що вимагає додаткового навчання.
- **Організаційне середовище.** Проєкт виконується в межах університетського курсу.
---

## 5.3. Аналіз зовнішнього оточення

- **Цільова аудиторія та її потреби.** Основна аудиторія - студенти закладів вищої освіти, яким потрібен єдиний зручний інструмент для контролю успішності, дедлайнів і відвідуваності без необхідності перевіряти кілька розрізнених джерел (журнали, дошки оголошень, месенджери).
- **Наявні аналоги та конкуренти:**
  - *Moodle* — популярна платформа з модулями оцінювання та дедлайнів, але з перенавантаженним інтерфейсом і слабкою персоналізацією для студента.
  - *Google Classroom* — простий у використанні сервіс для завдань і дедлайнів, проте не має статистики відвідуваності та функції прогнозування підсумкової оцінки.
  - Особисті кабінети деяких університетів (внутрішні системи деканату) - надають доступ до оцінок і розкладу, але зазвичай не мають аналітики чи прогнозних інструментів.
- **Технологічні тренди.** Зростає популярність персоналізованих освітніх дашбордів з елементами аналітики та простих ML/статистичних моделей прогнозування успішності, а також мобільно-орієнтованого дизайну.
- **Регуляторні чинники.** Оскільки застосунок обробляє персональні дані студентів (оцінки, відвідуваність), необхідно враховувати вимоги Закону України "Про захист персональних даних", зокрема щодо зберігання та обробки навчальної інформації.
- **Партнерські системи/API.** У перспективі можлива інтеграція з внутрішньою системою деканату або розкладом занять (за наявності відкритого API), що вплине на архітектуру та безпеку обміну даними.

## 5.4. Обмеження та припущення проєкту

### Обмеження

| № | Обмеження | Категорія |
|---|---|---|
| 1 | Проєкт має бути завершений до кінця семестру  | Час |
| 2 | Команда не має доступу до реальної бази даних оцінок університету | Ресурси |
| 3 | Розробка ведеться без бюджету на платні сервіси, хостинг чи ліцензії | Ресурси |
| 4 | Кількість учасників команди обмежена складом навчальної групи | Інше |
| 5 | Прогнозна модель оцінки має базуватися на простих статистичних методах | Технології |

### Припущення

| № | Припущення | Обґрунтування |
|---|---|---|
| 1 | Користувачі (студенти) матимуть стабільний доступ до інтернету та сучасного браузера | Цільова аудиторія — студенти, які активно користуються цифровими сервісами в навчанні |
| 2 | Дані про оцінки та відвідуваність вводитимуться вручну або через тестовий набір даних | На етапі розробки немає доступу до офіційних API навчального закладу |
| 3 | Базовий функціонал (оцінки, дедлайни, відвідуваність) буде затребуваний більшістю студентів незалежно від спеціальності | Проблема відстеження успішності є універсальною для студентів різних напрямів |
| 4 | Простий алгоритм прогнозування (наприклад, на основі зваженого середнього поточних оцінок) буде достатньо точним для демонстраційних цілей проєкту | Відсутність часу та даних для навчання складної ML-моделі |

5.5. Висновки

Класифікація проєкту як малого ітеративного веб-застосунку із середньою невизначеністю вимог обумовлює вибір Agile-підходу: функціонал уточнюється поетапно, а не фіксується наперед, як у каскадній моделі.

Найкритичніші чинники - обмежений часовий бюджет команди, відсутність досвіду в розробці прогнозних алгоритмів та брак доступу до реальних даних і API університету. Ці обмеження прямо визначають межі реалізованого функціоналу.

Основні ризики: низька точність прогнозної моделі через брак реальних даних; проблеми з відповідністю вимогам захисту персональних даних при подальшому масштабуванні.

Наступні кроки: зафіксувати базовий обов'язковий набір функцій (оцінки, дедлайни,відвідуваність); реалізувати просту статистичну модель прогнозування; розширення функціоналу та інтеграції - лише за наявності часу.
